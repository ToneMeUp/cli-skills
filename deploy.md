# Illumify — link, preview, build, upload

Load this before running the project locally, building it, or handing a theme over.

**Note the name.** This file is still called `deploy` because that is where the CLI's registry points,
and it is now a slightly misleading name: **there is no `illumify deploy`.** `upload` replaced it, and
the replacement moves no assignment. If you came here looking for a deploy command, the rest of this
section is the answer — including the part where an upload can nevertheless go live.

## The shape of the thing

Three entities, and only the middle one is yours:

| | Who owns it |
| --- | --- |
| **A storefront site** — its slug, access policy, customer links | A person, in the ERP. The CLI never creates one and never chooses a slug |
| **A theme** — a name you choose, holding immutable **revisions** | Your project. `illumify upload` creates the theme, then appends revisions to it |
| **An assignment** — which theme a shopper is served, and optionally which revision | An administrator, in the ERP. **No command here can move one** |

**Uploading and publishing are two acts, and only the first is ours.** An upload writes immutable
content. There is no `--activate` flag, no rollback, no "publish" — not withheld from you, absent by
design, because moving a live assignment is an administrative act and a developer tool must not expose
it.

**And an upload can still change a live site. Changed 2026-08-28 — this is the paragraph to read if
you read nothing else here.** An assignment points at a *theme*, with an optional pin to a particular
revision. Unpinned, which is the default, it serves the **newest** revision on every request. So
appending a revision to a theme a site already serves changes that site immediately, with no assignment
moved and nothing else done.

Both sentences are true at once. The CLI cannot publish, *and* your upload may be live the second it
finishes. `illumify upload` tells you which happened — four distinct answers, including "cannot tell" —
and that line is the one to read before you promise anybody anything. Do not carry over the older,
simpler rule that uploading is always invisible; it stopped being true.

What replaces "then open the URL" is a **hosted preview**: a short-lived capability URL that serves the
uploaded theme through the real renderer — real asset paths, real CSP, real pricing — without touching
an assignment. `illumify upload` mints one by default.

## Install the published CLI

Use the package from npm without a global install:

```bash
npx --yes @illumify/cli@<version> <command>
```

For a project-local command, install it as a devDependency with `npm i -D @illumify/cli`, then use
`npx illumify <command>` or the generated `illumify` scripts. A global install is also possible with
`npm i -g @illumify/cli`; do not install the unscoped `illumify` package.

### Two records, and they are not the same file

| | |
| --- | --- |
| `.env` | Which environment this project talks to. Generated by `illumify new` from its flags. **Gitignored** |
| `illumify.link.json` | Which storefront site it builds for and the optional remembered theme display name, per environment. Written by `link` and `upload`. **Committed** |

There is no theme id anywhere, and that is deliberate: upload discovers the logical theme by exact
display name. The first successful upload remembers that name in this environment's link entry. Later
uploads reuse it unless a new `--display-name`, or a deliberate edit to that field, chooses another
logical theme. The numeric server id is never trusted across hosts or companies.

## `illumify link` — and the gap you will hit without it

**A project scaffolded without `--profit-center` cannot upload until someone runs `illumify link`.** That
is inherent rather than an oversight: a theme is built *for* a site, and a site is created by a person in
the ERP. The CLI has nothing to invent.

**It can still be previewed, though — that is what `illumify dev --fixtures` is for**, and it needs no
link, no credential and no network. Against a real environment `illumify dev` gets the slug from the
link file or `--slug`, because it is asking somebody's catalogue for real answers. Fixtures ask nobody.
So "I have no site yet" is a reason to pass `--fixtures`, not a reason to wait.

```bash
illumify link --profit-center <id>
```

`--profit-center` is required; the ERP resolves the root company and the site's slug from it. Optional
`--company <id>` and `--slug <site-slug>` are assertions: a disagreement is refused. `--env` selects the
environment and `--api-host` (alias `--host`) overrides the host it implies.

It resolves the site and writes `illumify.link.json`. Run it once per environment — the ids are
meaningful only on the system they came from, so one environment's entry is never borrowed for another.
The from-scratch equivalent is:

```bash
illumify new . --env <env> --profit-center <profit-center-id>
```

Omitting `--profit-center` keeps `new` offline: no credential and no network. A company has one
storefront site and slug, though it may have several designs. `--company` is only an assertion of the
root company returned for the profit centre; it is not a lookup input.

`illumify link` is **read-only end to end.** It never creates a site, never creates a theme, and never
changes an assignment. What it does instead is *report*:

- what the site's default assignment currently points at, so if an upload is not going to change the
  live URL you are told in advance rather than debugging it afterwards;
- **whether the site allows anonymous shoppers at all.** A site whose access requirement is not
  `AnonymousAllowed` never serves an anonymous visitor the document: with sign-in enabled the request
  is redirected into sign-in, and otherwise it is a bare 404. Either way `illumify dev` — which
  replicates only the anonymous lane — is previewing a document no shopper is served that way, which
  is the point of printing the warning. (`illumify dev` itself always serves the document, so the
  divergence is silent unless you read the warning.)
- the addresses of the other authorities, when the site's own policy enables them — the customer-link
  and account URLs, which `illumify dev` cannot replicate;
- whether `signInRequiresInvite` is set, which **fails closed today**: invite administration and
  claiming are not implemented, so sign-in on such a site admits nobody.

Commit `illumify.link.json`. Its site ids and slug are ERP answers: do not hand-edit those; re-run
`illumify link`, which preserves a remembered display name. The optional `displayName` is the one field
you may edit deliberately to make the next upload address another logical theme.

## `.env`

```
ILLUMIFY_ENV=qa                               # local | dev | qa | prod — the environment's NAME
ILLUMIFY_API_KEY=                             # blank; a human's to fill. Rules below
```

That is the whole file a fresh scaffold writes. `illumify new` records the **one** flag it was given,
`--env local|dev|qa|prod`, and everything else is derived from it at run time: the URL segment, the
host and the backend shape live in one table inside the CLI, so `.env` cannot describe a combination
that does not exist. Two consequences:

- **`ILLUMIFY_ENV` is the environment's name, and the URL segment is derived from it.** A document is
  served at `/{segment}/services/main/storefront/{slug}` and its data under that path plus `/api`. For
  `local` the segment is `dev`, because that is the one the local stack answers on — the value you
  wrote is not always the word in the URL.
- **There is no setting for the host or the shape, and no flag for setting the shape against a
  different environment.** `--env qa` with a developer machine's path rewriting is a contradiction
  rather than a configuration, and it used to be writable. An old `ILLUMIFY_BACKEND_SHAPE` line that
  disagrees with `ILLUMIFY_ENV` is refused rather than obeyed; one that agrees is ignored. Do not
  reconstruct the shape by editing `.env`.

`ILLUMIFY_API_HOST` appears **only** when the project was scaffolded with `--api-host`, and it is an
override of the host the environment implies, not a required setting. If your `.env` has no such line,
that is correct. A value carrying a path — `https://host/qa/` — is wrong: the CLI appends the segment
itself, and the request would go to `/qa/qa/…`.

There is **no `ILLUMIFY_SLUG`** and no site id in `.env`. Those are the ERP's answers, and they live in
`illumify.link.json`.

`ILLUMIFY_SERVING_HOST` is an optional override of the *delivery* host, and the scaffold never writes
it. The one case where previewing and uploading are genuinely two processes on two ports — a developer's
machine, `--env local` — is derived from the environment like everything else. In every shared
environment the two lanes are one origin. If your `.env` has no such line, that is correct.

### `.env` is generated output, and it is not an agent's to edit

**The rule is about who is editing, not about the file.** The person who owns the project may change it
whenever they like — it is their environment, and when they change it they know they changed it. An
agent must not, because an agent's edit is invisible to that person: they will later wonder why the
project no longer matches the command that produced it, and nobody can tell which values were intended
and which were repairs. So if a value looks wrong, say what is wrong and leave it.

There is deliberately **no `illumify env set`**, and asking for one is the wrong instinct. A second
sanctioned way to change configuration would make the project reproducible from one command *plus
whatever env-sets happened afterwards, in an order nobody recorded*.

For one run somewhere else, use flags rather than the file:

```bash
illumify dev --env=qa --api-host=https://illumify.example
illumify dev --slug=<other-site-slug>
```

An explicit `--env` wins over `ILLUMIFY_ENV` in `.env` and says so with a one-line note on stderr; it
does not refuse the combination. `--api-host` outranks the environment's implied host. A flag lasts one
run; an edit outlives it.

Related, and for the same reason: **anything the scaffold generates that has to be hand-edited before
the project works is a defect in the scaffold, not a repair for you to make.** Report it.

## `illumify dev`

```bash
npm run dev
illumify dev --port 3000 --slug some-other-site --shopper-context identified --verbose
```

Also: `--fixtures [scenario]` (below), `--env`, `--api-host`, `--api-path-rewrite`, `--no-vite`,
`--no-open`.

A local replica of the **shopper lane**, not just a file server. It mounts the document under its real
prefix (`http://localhost:3000/{env}/services/main/storefront/{slug}`), routes by your `pages`
with the same exact matching, injects the server's own bootstrap so the page gets the same frozen
`window.IllumifyStorefront`, and proxies the API upstream. For a Vite project it runs Vite underneath,
HMR socket included.

The slug comes from `illumify.link.json`, not from your config — which is why an unlinked project needs
either `--slug` or `--fixtures`, below.

### `--fixtures` — the same replica with nothing behind it

```bash
illumify dev --fixtures                 # the `catalog` scenario
illumify dev --fixtures empty           # or: windowed, restart
illumify dev --fixtures --shopper-context identified
```

**No link, no credential, no network.** The catalog API is answered inside the `illumify dev` process:
no host is read, `ILLUMIFY_API_KEY` is not attached anywhere, and no request leaves the machine. Everything else is the same replica as always — the document is mounted under its real
prefix, routed by your `pages` with the same exact matching, and injected with the same bootstrap.

So a project straight out of `illumify new` can be previewed **before a storefront site exists**, which
is the whole point: somebody working on how a page looks should not have to ask an administrator for a
site first. It is also the honest answer to "I cannot preview because I am not linked yet".

**The catalogue is deliberately awkward**, because a fixture that is tidy teaches a page that only works
on tidy data. Missing prices are `null` and never `0`, an item can be visible and unorderable, one SKU
carries several offers across UOMs and batch grains, and the recommended offer is not the cheapest.

| Scenario | What it is for |
| --- | --- |
| `catalog` (the default) | Eight SKUs with all of the above on screen at once |
| `empty` | `items: []`, every facet empty — the case a grid built against three tidy products gets wrong first |
| `windowed` | 5,200 SKUs, so delivery is `windowed` and `nextCursor` has to be walked |
| `restart` | `windowed`, and the revision moves once: one `409 CatalogRevisionChanged` on page two, then the walk completes |
| **`facilities`** | A known customer with **three eligible facilities**, so the server chooses none and the whole catalogue arrives unpriced until you send a `customerFacilityKey` |

`restart` is worth knowing about: it is the only way to exercise the 409 path before a live shopper
does. `illumify skills get data` explains what that path has to do.

**`facilities` is the one that decides what you build rather than how you cope.** Every other scenario
shows you data your page has to survive; this one shows you a page that cannot work. A shopper with more
than one eligible facility gets `unitPrice: null`, `effectiveUnitPrice: null` and `available: false` on
every offer, `available: false` on every item, and `pricingContext: "Customer"` reported all the same —
a complete catalogue that looks like a seller with nothing in stock, with no error anywhere. `msrp` is
*not* suppressed, so a page with an `?? msrp` fallback prints a plausible number beside an offer it
cannot buy.

```bash
illumify dev --fixtures facilities
# then: GET {apiBaseUrl}/session            -> facilityList has three entries
#       GET {apiBaseUrl}/items              -> 200, and not one price
#       GET {apiBaseUrl}/items?customerFacilityKey=<one of them>   -> priced
```

Each facility prices from its own segment, so the three keys really do give three different numbers —
which is what makes a column layout worth testing here. The keys are **opaque**: pass one back exactly
as `session` gave it, and an unknown or hand-made one is a bare `404`, as in production. It overrides
`--shopper-context`, because an anonymous shopper has no facilities at all and "anonymous with three
facilities" is not a state the server can produce. `illumify skills get data` has the rule.

Two things behave differently here than they do against a real environment, and both are in the banner:

- **`--shopper-context identified` is not cosmetic under `--fixtures`.** The fixtures own the answer, so
  `pricingContext` really becomes `Customer` and the numbers on screen change. Against a real
  environment the same flag only changes the label the page is told.
- **A call to any Illumify operation that is not the shopper API answers `501`** rather than reaching a
  backend. Nothing is proxied, so there is nothing to reach.
- **The cart and checkout routes answer `501` with a body saying they are not emulated**, and the status
  is chosen rather than inherited: a bare `404` is what the catalogue sends for everything that fails,
  so it would read as "this platform has no cart". These three routes are real in production. They are
  not emulated because their request and response shapes are not generated contracts the CLI can check
  itself against the way it checks the catalogue's, and because a fixture cart answering `200` would be
  the only place a storefront write succeeds without the `Origin` check production applies first — which
  would teach you that a write path works when the first thing production does is refuse it.
  Cart code still *runs* here: the four methods are on the runtime. Exercise the far end on the hosted
  preview an upload gives you.

**Fixtures live in the CLI binary, not in your project.** There is no fixture file for a build to pick
up, so none can reach an uploaded theme.

### It replicates the anonymous lane, and only that one

A document is served under one of four authorities. Dev serves **anonymous**, because it is the only
one it can serve honestly: a customer-link token and a preview capability are server-minted secrets,
and an account document needs a real identity through the auth bridge.

An **exact** preview of the other authorities is what `illumify upload`'s hosted preview gives you.

### The divergences, stated as a list because each one has cost somebody an hour

| Deployed | Under `illumify dev` |
| --- | --- |
| `config.themeKey` is the theme's key | **Absent.** Nothing has been uploaded, and a made-up 64-character key would name nothing while reading as an answer |
| `getSession().themeKey` is that same key | **`null` under `--fixtures`**, for the same reason. The SDK types it as `string`, so a page that renders it prints `null` with no type error. Widening that type is the SDK's to do; do not paper over it here. `config.themeKey` is the one declared optional, so prefer it |
| `login` / `logout` are functions | **`null`.** The auth bridge is a deployed route. The DOM hooks are wired and the click does nothing |
| A strict CSP on every document | **No CSP header at all.** A third-party fetch or a CDN script works here and fails deployed |
| `accessMode` varies by how the shopper arrived | Always `"Anonymous"` |
| The server resolves the shopper | `--shopper-context identified` changes **only the label the page is told.** The upstream calls still go to the anonymous lane with no credential, so the server resolves `Anonymous` for them. Use it to check that your identified rendering exists, not to test pricing |
| `getCart`, `replaceCart`, `prepareCheckout` and `checkout` reach the cart | **The methods are there and the writes do not land.** They are on the runtime — dev injects the server's own bootstrap, `version: 2` and all — so your cart code runs and your types are right. What differs is the far end: **under `--fixtures` the three cart routes are `404`** (the fixture server answers `session`, `items`, `items/{skuId}` and `filters`, and nothing else), and against a real environment the write is refused, because the platform compares the browser's `Origin` against the storefront's own and the browser's origin here is `localhost`. Build the cart in dev, exercise it on the hosted preview an upload gives you |

Read every one of these defensively and your page behaves correctly in both places. That last row is
the safe direction and worth reading as one: a dev preview **cannot** write into a real shopper's cart
or place a real order by accident. **Do not add a
dev-only shim to make the button work locally** — a shim that compensates for the platform is exactly
the divergence that has cost this project hours before: the preview works, the deployed page does
something else, and nobody is watching the half that differs.

### Other things it does deliberately

- **A 404 is a bare 404**, and there is no fallthrough: a request for a file under your document path
  is 404ed here exactly as it would be deployed, rather than helpfully served.
- **A request for an *uploaded* theme's asset path is 404ed** before the API proxy sees it. Proxying it
  would fetch a deployed theme's files into a preview of your working copy — a page that renders, from
  somebody else's build, with nothing saying so.
- **Product media is proxied**, so a preview shows the same pictures a shopper sees.
- **It serves the server's content-type table including its gaps.** `.map`, `.txt` and `.xml` come back
  as `application/octet-stream` here exactly as they would deployed.
- **`illumify.config.ts` is reloaded while it runs**, and the terminal names each route added, removed
  or repointed. That matters because matching is exact: a route merely close to the one you typed is a
  404, not a near miss. A config that does not compile leaves the previous one serving rather than
  killing the server mid-edit.

### Ports

Default `3000`. A busy port moves to the next free one and says so. A sign-in started from a preview
only returns to a port the deployed allowlists contain — `localhost:3000` and `localhost:3600` — which
matters only for a page that signs a buyer in through the browser. The shopper lane needs no sign-in at
all.

### Path rewriting

`--env local` implies the local backend shape — nothing is written to `.env` for it — which rewrites
`/{env}/oauth2/` to `/oauth2/` and nothing else — **no service path is ever rewritten, under either shape.**

That absence is deliberate and was paid for. A development-only rewrite that compensates for a client
defect makes the preview *less* faithful, not more: a working preview once hid a deployed site that
answered 401 on every call, for hours, because the proxy was quietly repairing paths in dev that
nothing repaired in production. If a path is wrong, it is wrong in the client.

If a data call 404s and no rewriting is configured, `illumify dev` prints an explanation with the flag
to add — but **verify the target exists before setting one.** A rewrite pointing at an address the
backend no longer serves turns a legible 404 into a proxy's 403, which is harder to read and one layer
further from the cause.

A project written before the shape was derived may carry `ILLUMIFY_PRESET` or `ILLUMIFY_BACKEND_SHAPE`.
The first is refused, naming the `ILLUMIFY_ENV` value to set instead; the second is refused only when it
disagrees with `ILLUMIFY_ENV`, and is otherwise ignored.

## `illumify build`

```bash
npm run build
illumify build --author-version 1.4.0 --out-dir dist --no-bundle
```

In order — and the order is the interesting part, because it is the reverse of what a bundler-first
toolchain does:

1. Runs your own build (`build:app`) with **no asset base at all**. The theme is built base-relative;
   `vite.config.ts` carries `base: "./"`.
2. Collects the output and **stages** it: refuses anything the server would refuse, reads every byte.
3. Checks the manifest's claims and every link in every document.
4. **Derives** the `themeKey` — 64 lowercase hex characters — from the keyless manifest plus every
   file's path and bytes.
5. Finishes the manifest with that key and **seals** it into the archive as `manifest.json`.

**Why the key is last, and why that matters to you.** The asset base contains the theme key, and the
key is a hash of the theme's content — so a value the bundler would need *before* producing the content
cannot be derived from it. One of the two had to go, and the baked-in base was already a known defect.
So: `base: "./"` stays, the server declares the real base at serve time, and **there is no
`ILLUMIFY_ASSET_BASE`.** Do not reintroduce one.

**This key is local, and it is not what the server stores. Changed 2026-08-28.** The server derives its
own key for every revision — from the archive, the manifest text, your company id and the display name —
and uses that in preference to the one in the manifest you send. So the key `illumify build` prints and
the key `illumify upload` reports back are **different values by design**, and comparing them is an
error: it would report every working upload as a broken one.

What the local key still buys you is reproducibility you can check without a server: the same commit
built twice on two machines derives the same value, so you can tell two builds apart, or recognise one,
offline. What it no longer does is predict the theme's name on the platform.

The idempotence moved with it. **Uploading identical content twice still writes nothing the second
time** — that is what makes `illumify upload` safe to run from CI on every commit — but the server
decides it, by comparing its own hash of the content. You cannot compute that hash locally.

The corollary is unchanged: the manifest is part of the identity. Editing `illumify.config.ts`, or
bumping `authorVersion` (which defaults to `package.json`'s `version`), produces **different content**
from the same files, so it is a new revision even when every page byte is identical.

**A build is no longer bound to one environment.** A base-relative theme carries no environment, so the
same archive uploads anywhere. `--env` only decides which host the report and the hand-off text
address.

### The manifest is inside the archive, and the archive is the whole upload

**Changed 2026-08-20.** The manifest used to travel as a separate `manifest` form field and the archive
deliberately carried none. Now `illumify build` seals `manifest.json` into the archive and `illumify
upload` sends **one** field, `theme`.

Why not both: the server reads the `manifest` form field first and falls back to the archive's copy
**only when that field is blank**. So with both present the copy a person can open is the copy that
loses, silently. One source, and it is the legible one.

**Never attach a `manifest` field by hand** — to a `curl`, to a CI step, to anything. It would take
precedence over the manifest inside the archive, and nothing prints the difference.

This did not change any theme key when it landed. The local key is derived from the staged files and
the keyless manifest, *before* the manifest is sealed in, so the manifest is never an input to its own
name. The server's `contentHash` is computed over a canonical archive it rebuilds with `manifest.json`
filtered out, so that was unchanged too — which is why a theme built before the change and rebuilt
after it re-uploads as the same content.

(A sentence that used to sit here — "the server never derives a key at all: it validates
`^[a-f0-9]{64}$` and stores what you send" — was true until 2026-08-28 and is not. See **`illumify
build`** above.)

**Do not put a `manifest.json` in your build output.** It would race the one the packer writes, and the
server reads whichever it finds as *the* manifest. `illumify build` refuses the build and names the two
ways it happens: a bundler emitted one (Vite's `--manifest` used to write `dist/manifest.json`), or a
downloaded theme was unpacked without dropping the server's own copy.

### Outputs, and where they are not

The ZIP and a readable manifest go into **`.illumify/`**, in the project root and **outside the upload
set**. That is not tidiness: anything inside the output directory is uploaded, so a `manifest.json`
there would collide with the packer's. `.illumify/theme-manifest.json` is the same JSON
pretty-printed — a **rendering**, for reading, since the authoritative copy is one compact line inside
a ZIP. Nothing sends it and nothing hashes it. It is not called `manifest.json` for the collision
reason above.

**A rebuild does not clear the retired contract's artefacts.** A project built before the Buyer Website
retirement may still hold `.illumify/site-package.zip` and `.illumify/site-manifest.json`; the new names
are different, so both pairs sit there. `illumify build` names them when it finds them and deletes
nothing — they are yours. Upload `theme.zip`, and do not attach `site-manifest.json` as a field: it is a
manifest from a contract that no longer exists, and the field would beat the archive.

### What it checks

- **Every `page.entry` exists** in the build output.
- **Every file's extension is on the server's allowlist.** One file outside it refuses the whole ZIP —
  see `illumify skills get app` for the list and the other archive limits.
- **Every link resolves against the theme root**, because that is where `<base href>` points. Two
  failures it names:
  - *"resolves above the theme root"* — a `../` prefix, which is what a bundler emits for a nested
    entry with a document-relative base.
  - *"an absolute path resolves against the origin root"* — `/assets/app.js` points above the
    environment segment and above the theme, so it can never reach a theme file. Reported whether or
    not a file of that name exists.
- **Every file the server has no content type for**, named as a warning. Not a gate — the file may
  never be fetched — but a browser will not execute a module script or apply a stylesheet served as
  `application/octet-stream`.

`illumify build` refuses nothing on broken links. `illumify upload` reports them and proceeds, because a
broken link is a 404 for a shopper and not a reason to block the upload. This is a dangerous success:
a theme whose scripts resolve to the origin root can serve a blank page. Keep `base: "./"` in
`vite.config.ts`; never restore `base: process.env.ILLUMIFY_ASSET_BASE ?? "/"`, because that variable is
never set.

An **author version is never invented.** A project whose `package.json` has lost its `version` is told
to add one or pass `--author-version`, rather than having something like `0.0.0` stamped on every theme
every customer ever ships.

## `illumify upload`

```bash
npm run upload -- --display-name "Multi-Facility Checkout"  # first upload, or choose another theme
npm run upload                                                # reuse the remembered name
illumify upload --no-preview --preview-as-customer <id> --author-version 1.4.0
```

Also: `--env`, `--api-host`.

**It builds the theme itself**, so you cannot upload a build made somewhere else. Before it builds it
**reads the site from the ERP** and **looks up the flag or remembered display name**, so a wrong host, a
wrong environment, a rejected credential, a deleted site or an ambiguous name fails in a second rather
than after a full bundle.

### A theme is a name holding revisions — changed 2026-08-28

`--display-name` is not a label attached to each upload. It is the theme's **identity**, and it is how
this command decides what to do. The first successful upload stores the trimmed name as `displayName`
in this environment's `illumify.link.json` entry; after that the flag is optional. A supplied flag wins
and replaces the remembered value only after success. Editing that field has the same deliberate effect.

| What it finds | What it does |
| --- | --- |
| No theme of this name | `POST /storefront-themes` with `displayName` + `theme` — creates it, revision 1 |
| One theme of this name | `POST /storefront-themes/{id}/revisions` with `theme` alone — appends |
| Two or more | **Stops.** It will not choose, and it prints the colliding ids |

Three things follow, and each has bitten somebody:

- **You cannot rename a theme.** The revision endpoint takes no display name — the server reads it off
  the theme — so uploading under a different name does not update anything, it *addresses a different
  theme* and creates it if it is not there.
- **A typo makes a second theme, not an error.** There is nothing for the server to refuse: an unused
  name is exactly what a first upload looks like. Check `illumify themes list` if a theme you expected
  to grow a revision has stayed at one.
- **The name is matched exactly**, after trimming, NFC normalization and a case-insensitive fold.
  `"Checkout"` and `"Checkout "` are the same theme; `"Checkout"` and `"Checkout v2"` are not.

Then it reports, and the reporting is the part worth reading:

- **Three outcomes, not two.** `created` — this name was new here. `revision-created` — the name
  existed and now holds one more revision. `unchanged` — the server already had exactly this content
  and wrote nothing. The last is not a no-op to apologise for; it is what makes this safe to run from
  CI on every commit. The body is identical in all three cases, so the status and the endpoint are the
  only places the difference lives.
- **`409` is two situations now and `illumify upload` tells them apart** off the server's stated
  reason. Both arrive as a bare `409`.
  - **A theme with this name already exists.** You should not see this: the lookup above exists to
    catch it first. If it appears, the CLI and the server disagree about what is stored — usually
    because somebody uploaded the name in between, in which case re-running now appends to it.
  - **The stored content is incomplete.** A row exists whose content hash matches yours and its blobs
    are not all there. A theme uploaded before the canonical archive existed is permanently
    incomplete — there is no backfill — and has to be cleared by whoever administers the environment.
    A *failed* upload looks identical and often clears itself, so retry once first. **Changing
    anything** also works and is usually faster: different content is a different revision, stored
    fresh.

  A third one used to be here — an unchanged copy of an Illumify-provided theme colliding on a
  content-derived key. **The platform can no longer produce it**, because the server's key now folds in
  your company id and the display name. If you are reading older notes that tell you to change a file
  to get past that `409`, ignore them; it never comes.

### Uploading moves no assignment, and can still change a live site

Both are true, and holding only the first is how somebody tells a customer the page is not live when it
is. Assignments point at a *theme*, with an optional pin to a particular revision. **Unpinned — the
default — an assignment serves the newest revision on every request.** So appending a revision to a
theme a site already serves changes that site the moment the upload commits, with no assignment
touched and nothing else done.

This CLI still cannot publish, roll back, or move an assignment or its pin. All of that is
`ThemeAssignmentPersist`, in the ERP.

- **What the site now serves, or a clear statement that this cannot be told.** Four answers, and they
  are genuinely four:
  - **Live** — the site's default assignment points at this theme and follows the latest revision, so
    this upload is what shoppers get. The URL is printed.
  - **Pinned elsewhere** — the assignment points at this theme but is pinned to another revision, so
    your upload is stored and not served. Moving the pin is an administrative act.
  - **Not live** — the assignment points at a different theme, or there is no default assignment. The
    URL is *withheld* rather than printed with a caveat: printing it would answer "where is my page"
    with a page that does not contain what was just uploaded.
  - **Cannot tell** — the assignment points at this theme and the response did not say whether it is
    pinned. Unpinned it is already live; pinned it is not. Guessing either would be a fact-shaped
    guess, so it says so instead. Read the assignment in the ERP.
- **Do not compare the reported `themeKey` with the one `illumify build` printed.** They are different
  values by design; see **`illumify build`**.
- **Other assignments that already point at this theme**, since a theme reachable by a customer segment
  or a named customer is reachable even when a plain visit to the slug gets something else.
- **A hosted preview URL and when it expires.** `--no-preview` skips it. `--preview-as-customer <id>`
  prices the preview as a particular seller customer instead of a public shopper — which is the only
  way to see customer pricing without being one.

**Then open the preview and use the page.** A successful upload is not the same as the pages working.

## `illumify handoff`

```bash
illumify handoff --out theme-bundle.zip
```

Builds, then writes **one file** somebody else can upload without this CLI:
`.illumify/<project>-<version>-handoff.zip`, holding the archive and a `README.md` written for whoever
receives it. The manifest is inside the archive, so there is nothing else to carry.

It used to hold a loose copy of the manifest too, because the endpoint took two fields. It no longer
does, and the removal is deliberate: a `theme-manifest.json` sitting beside `theme.zip` in an unpacked
bundle is an invitation to send it as `-F manifest=@…`, which the server takes **in preference to** the
archive's own copy. Everything a person reads off a manifest — the key, the version, every route and
entry — is printed in the README instead.

The archive is the same byte string `upload` sends, from the same accessor — so "the thing you hand over
is the thing that uploads" is true by construction. With a content-derived key that matters more than it
sounds: **a re-zip would name a different theme than the manifest sealed inside it claims**, and the
server would refuse the pair.

It talks to nothing and needs no credential, so a hand-off can be made on a machine with no access at
all.

## `illumify themes` — what you can start from

```bash
illumify themes list                  # in a linked project
illumify themes start <REVISION_ID>   # anywhere, with a credential
```

**Every theme owned by Illumify is available to every customer.** `themes list` preserves the API's
newest-first order: `ThemeGetList` returns this root company's themes plus Illumify's. The listing puts
the stored display name first, then the theme id, how many revisions it holds, and the newest
revision's own id, key, author version and upload audit.

**`themes start` takes a revision id, not a theme id — changed 2026-08-28.** A download is one exact
set of bytes, and a theme id no longer names one. The listing prints both; the one you want is on the
`revision … id` line. The URL kept its shape, so passing a theme id is not refused as the wrong kind of
thing — it names a different revision, or none, and you get a `404`.

The two halves need different things and it is worth knowing which:

| | needs |
| --- | --- |
| `themes list` | a linked project — that is where your company id lives |
| `themes start` | only a credential — the archive endpoint resolves your tenant and asks for no site |

(`ThemeGetList` used to require a `storefrontSiteId` too. It no longer does; the list was always
company-wide, and the site only ever scoped authorisation.)

The credential is the `ThemeGetList` permission, Full or View Only. A `404` covers several situations
on purpose — a theme id passed where a revision id belongs, no such revision, somebody else's,
incomplete stored content, or no tenant scope — because a refusal that named itself would tell a
stranger what exists. The CLI spells them all out.

### What you get, and what it is not

**A downloaded theme is built output, not source.** It is HTML, CSS, already-bundled JavaScript and
images. So the project you get has no bundler, no `@illumify/sdk` dependency and nothing to install:
`theme/` holds the theme's files and they are the source. Edit them directly; `illumify build` packages
them as they are.

`theme/` is **committed** — it is the only thing in the project worth committing. It is deliberately not
`dist/`, which `.gitignore` ignores.

**The server's `manifest.json` is stripped on the way in.** The download carries one; it names the theme
you started *from*, and `illumify build` writes a fresh one. Leaving it would collide with that. Do not
add it back.

**Uploading an unchanged copy is a no-op, not a refusal — changed 2026-08-28.** It used to answer `409`,
because a theme was named by a hash of its content and an unchanged copy carried the shared theme's own
key. The server's key now folds in your company and your display name, so an unchanged copy uploaded
under your own name is simply *your* theme, created normally. Uploading it a second time writes nothing
and says so.

If you only want the shared theme served, you do not need to upload at all — ask whoever administers the
site to assign it.

### It is not `illumify new --template`

Two different namespaces and two different credentials. `--template` takes a *name* and is meant to work
with no host and no key; a theme is a per-environment row id behind an authenticated endpoint. And
`--list-templates` answers offline from the templates built into this CLI, which `ThemeGetList` cannot
do. They stay separate commands.

## The credential: one key, three places

`illumify link`, `illumify upload`, `illumify themes` and the proxying lane of `illumify dev` share
**one** credential, `ILLUMIFY_API_KEY`. Understand what it is before you go looking for one: an API key
here is a **full-rights ERP user credential** — no scopes, and no expiry at all. It is not an
upload-only token and there is no lesser version of it.

The CLI looks in exactly three places, in this order, and the order is the same on localhost and on a
shared environment:

1. **`--api-key <key>` on the command line.** One run. It lands in shell history and the process
   list, which is why it exists for development and is not the documented way to hold a key.
2. **`ILLUMIFY_API_KEY` in the process environment.** The CI source, from a masked secret.
3. **`ILLUMIFY_API_KEY` in the project's gitignored `.env`.** The developer-machine source.

That is the whole list. There is **no OS keychain lookup, no saved session, no loopback placeholder and
no `illumify login`** — those belonged to an earlier design and were switched off by the product owner;
`login`, `logout` and `whoami` are not commands. A blank or `Bearer`-only value counts as absent, and a
missing key stops a control-plane command before it builds anything, naming the two supported places.
`ILLUMIFY_DEV_API_KEY`, the separate dev-proxy key of the earlier design, is **not read**: a project
that still carries it has a line the CLI ignores and no credential.

The CLI prints which source it is using before it talks to the server, so the consequential choice is
visible: `(credential: --api-key)`, `(credential: ILLUMIFY_API_KEY)` or `(credential: .env)`.

**If a command's error mentions credentials, check the environment and the host first.** A redirect or a
404 from the upload path is about the URL, not the key — and inventing a fake key to get past it is
precisely the habit this section exists to prevent.

### If you are an agent working in this project

**Do not ask the human to paste the key to you, and do not accept it if offered.** A pasted key lands
in this transcript, and in any log or context store behind it, permanently — and it is a credential that
never expires and cannot be scoped down. There is nothing you can do afterwards that un-leaks it.

**If a command fails with 401 or reports no credential, stop and hand back.** The remedy is a human
action at their own terminal, and the CLI prints the exact setting for it. Do not:

- write the key into `.env`, `.env.example`, a shell profile, a script, or any file;
- echo, log, or repeat the value anywhere, including "just to check it";
- work around a missing credential by looking for one elsewhere on the machine.

**Do not read the value of `ILLUMIFY_API_KEY` either — unless the owner directly tells you to.** That
exception is theirs to give and it is real; short of it, ask them to set the key and stop. The existing
rule about `.env` is that you must not *edit* it. This key adds: do not *read* it, and do not put it in
a message, a commit, a log, or a note. A value that reaches a transcript is leaked permanently, and
**this key does not expire**, so there is no point at which the leak stops mattering. Revocation is the
only remedy, and it is the owner's to perform.

Everything that talks to nothing works without it: `illumify build`, `illumify handoff` and
`illumify dev --fixtures` need no credential at all.

## What `illumify dev` does with the same key

**The shopper API takes no credential at all, ever**, and `illumify dev` attaches nothing to it. Plain
requests to `/api/session`, `/api/filters` and `/api/items` answer without an auth header, so a preview
shows real catalogue data and prices with `ILLUMIFY_API_KEY` blank. If your pages only read the
catalogue through `@illumify/sdk`, the rest of this section does not apply to you and a blank slot in
`.env` is correct as it stands.

Anything **outside** the shopper API is a different matter. An ordinary Illumify service operation needs
an ERP session, and `illumify dev` has none — so when `ILLUMIFY_API_KEY` is set it attaches that key
upstream instead, on every non-shopper service path, and says so in its banner. The key never reaches
the page: it travels from the dev process to the server and nowhere else.

**Before you reach for it, ask whether the feature belongs in a theme at all.** A deployed shopper is a
buyer, not an Illumify user, and holds no ERP session — so a call outside the catalogue reads cannot
work for the audience the site is for. It will not start working later and there is no flag that makes
it work. The key is for reaching data *during development*, not for building a shopper-facing feature
on.

**This is the platform's own pattern rather than something invented for this CLI**: attach a header
credential in development, rely on the deployed request's own authority afterwards. The SDK sends no
`Authorization` header in any environment precisely so that the development half can live here, in a
process outside the browser.

### How a human creates one

**On the ERP's API keys page** — your profile → API keys, at `{identity-host}/{env}/identity/api-keys`
for the environment this project points at. Create a key, copy the `tone_live_…` value it shows once,
and put it in `.env` as `ILLUMIFY_API_KEY=…`.

The page needs a browser session, so this is a human action at a browser and there is no CLI command for
it. **Name the key after the project** — the list shows names and prefixes, and that is how you find the
right one to revoke later.

### It does not expire. Revocation is the mitigation

**A key from that page has no expiry at all**, and the page has no field to ask for one — it takes a
name and nothing else. Do not assume there is a shorter-lived variant you could have picked instead;
there is not one on that page.

So do not treat this as something that ages out:

- **name it for the project**, so it can be found;
- **revoke it on the same page when you are done** — that is the off switch, and the only one;
- **one key per project**, never a shared one, so revoking has a known blast radius.

It carries your full claims — your tenant and every security account you can reach. That is why one
key is enough for both uploading and previewing, and why it may live in exactly the three places above.

### The dev half is dev-only, and structurally so

The code that attaches the key lives inside `illumify dev`, which is **never deployed**, and the value
never enters JavaScript so no bundler can put it in a built asset. A deployed page carries **no
credential at all** — its authority is the URL it was served under. You do not have to remember to
remove anything before shipping, because there is no path by which it ships.

**A long-lived key in a project file is the weakest part of this arrangement**, and it is expected to
be replaced. Treat it as something to revoke when you are done rather than something to keep.

If a call outside the shopper API is refused while you are working, say so and name this key as the
likely cause. Setting it is the owner's action at their own browser.

## When something does not work

The shopper routes were **not yet proxied on the shared environments** when this was written — the
storefront prefix answered a redirect, which is the signature of an unrouted prefix. So a redirect or a
404 from a document or catalog path is as likely to be that as anything in your project.

Say what you ran, what you expected and what happened, and stop. Do not work around a broken tool by
reaching into Illumify's own source, do not invent a credential to get past an error, and do not invent
data to make a page render — a page showing invented products is worse than one showing an error.
